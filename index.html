Urban analytics · In progress

Graph-based Neural Network for Informal Settlement Characterization

Luanda · Dhaka · Munich

Project overview

Look at a satellite image of almost any large city in the Global South and you can usually spot the informal settlements. The buildings are smaller, closer together and laid out with less regularity than the neighbourhoods around them. This project asks whether a model can learn that pattern from building footprints alone, without needing imagery at all.

  • Python
  • PyTorch
  • GeoPandas
  • Graph Convolutional Networks
  • Graph Attention Networks

Why graphs?

A single building says very little on its own. What makes a settlement informal is how buildings relate to each other: how close they sit, how they are oriented, and how dense the cluster is. A graph captures that naturally. Each building becomes a node, and neighbouring buildings are joined by edges, so the model learns from both the footprint and its surroundings.

Data

Labelled building footprints from Luanda and Dhaka are used for training and evaluation. Munich is held out as an out-of-domain test: a city with a very different urban form, used to check whether the models have learned something general or simply memorised the training cities.

Approach

I compare two graph neural network architectures, Graph Convolutional Networks (GCN) and Graph Attention Networks (GAT). GCNs treat all neighbours equally, while GATs learn which neighbours matter most. Comparing them shows whether that extra flexibility helps on building layouts.

Status

Work in progress. I'm writing the results up as a short paper and plan to build on it, including testing on more cities. Findings will be added here once the analysis is complete.

Earth observation · In progress

Environmental Indices Analysis Platform

Sentinel-2 · any area of interest

Project overview

My STAC pipeline made it easy for me to compute vegetation indices. This project makes it easy for anyone. You upload a boundary or draw a box, choose a date range and an index, and the platform returns a time series, a chart and a map you can download. No code required on your end.

  • Python
  • FastAPI
  • Dask
  • STAC
  • xarray
  • Streamlit
  • Docker

What it does

The platform computes NDVI, EVI and SAVI for vegetation, and MNDWI for surface water, over any area and period covered by Sentinel-2. For each index it returns a time series, a chart, and a composite image as both a PNG for quick viewing and a georeferenced GeoTIFF for use in GIS software.

How it works

A Streamlit front end sends each request to a FastAPI service, which does the heavy lifting with Dask.

What I learned along the way

Two bugs taught me the most. Early on, EVI values were wildly off. Sentinel-2 stores reflectance as integers up to 10,000, and I was feeding those raw numbers into formulas that expect values between 0 and 1. Scaling each collection properly before any index math fixed it.

The second was quieter. The engine fetched all four bands for every request, even when NDVI only needs two. Fetching only what each index needs roughly halved the run time, with identical results.

Status

The full stack runs end to end in Docker, with the API and front end as separate services. Deployment to AWS is the next step.

Mobility Analysis from Call Detail Records

Call detail records · 1.5M users

Project overview

During the COVID-19 lockdowns in 2020, governments used mobile network data to check whether movement restrictions were holding. Call Detail Records (CDRs) make that possible: every connection to a cell tower leaves a trace that estimates where a user is over time. This project builds the processing side of that idea, a PySpark pipeline that turns raw CDRs for 1.5 million users into per-user mobility metrics.

  • Python
  • PySpark
  • Pandas UDFs
  • NumPy
  • Seaborn
  • Matplotlib

Objectives

Process call records for 1.5 million users with PySpark, generate summary statistics, and explore the relationship between the average number of unique locations per user per day and the average radius of gyration.

Data

Call records for 1.5 million users over 14 days, from 29 June to 13 July 2018. Each record is joined to cell-tower coordinates, and records missing a cell ID, latitude or longitude are dropped.

Methods and workflow

Preprocessing runs in Spark. The radius of gyration, the distance a user typically moves from their centre of activity, is computed with a pandas UDF, which is much faster than converting the Spark DataFrame to pandas first. Repartitioning, caching and sampling during debugging keep the pipeline scalable.

Findings

Activity per user is heavily skewed: the median user has 3 records, the mean is about 7.8, three quarters of users have 8 or fewer, and the most active user has 8,277. Average radius of gyration and average unique locations per day are positively but modestly correlated (r = 0.32).

STAC Vegetation Index Pipeline

Catalog-agnostic

Project overview

Satellite imagery is everywhere, but getting from a STAC catalog to a clean, analysis-ready raster still takes more effort than it should. This module removes that friction: pass in a bounding box, date range and cloud-cover threshold, and it returns vegetation indices as Cloud-Optimized GeoTIFFs.

  • Python
  • STAC
  • pystac-client
  • stackstac
  • xarray
  • Rasterio
  • Cloud-Optimized GeoTIFF

Purpose and use case

The pipeline is built around pystac-client and stackstac. It queries any STAC-compliant catalog and loads only the imagery that intersects your area of interest, so unnecessary data never enters memory. It computes NDVI, EVI and SAVI, and writes results that open directly in QGIS, GDAL and cloud-based raster APIs. The workflow is fully parametrized, designed for reproducibility and scale.

Inputs and configuration

Three parameters drive a run: a bounding box, a date range and a cloud-cover threshold. The STAC catalog is a configurable source, so the same code runs against any compliant endpoint.

Processing workflow

From user parameters to exported rasters, in six steps.

Outputs

Each run exports Cloud-Optimized GeoTIFFs, ready for QGIS, GDAL and cloud-based raster APIs without conversion.
